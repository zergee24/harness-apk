# ADR-0001：控制面放在常驻的 Mac mini，手机是一等客户端

日期：2026-10-30

状态：**已决策**（授权分档待首次真机验收）

## 1. 背景

### 1.1 硬件事实

用户的 Mac mini 7×24 开机。这台机器就是"常驻执行环境"，不需要租用云端虚拟机，数据也不离开本机。

这条事实消解了上一轮讨论的核心约束：任务账本放在哪里，取决于哪里 7×24 在线。

### 1.2 当前实现的位置

- Bridge 已经拥有 Run 协调、逻辑事件 Journal、完成证据、幂等指令这些零件。
- 但 Bridge 对外仍主要扮演**转发器**：把 Codex app-server 的事件转给手机。
- 任务状态在日常使用上仍围绕 Codex 的 Thread / Turn 组织，App 侧保存的 Run 账本是对 Mac 状态的**镜像**。
- 结果是：任务身份长在具体 harness 上，换执行器就断代；手机离线时任务停在非终态。

### 1.3 参考产品的位置

| 产品 | 控制面在哪 | 手机是什么 |
| --- | --- | --- |
| Dots / Muse / Grok Bot | 云端常驻 VM | 客户端 |
| OpenClaw | 你的电脑（Gateway） | 渠道之一 |
| 本项目（现状） | 没有真正的控制面 | 遥控器 |

成熟产品没有一个把任务账本放在手机上，原因是手机会关机、会没电、会被系统回收。既然本机已经 7×24，账本就应该放在 Mac 的 Bridge 上。

## 2. 决策

1. **控制面在 Bridge（运行于常驻 Mac mini）。** Bridge 持有任务账本，是"进度"的唯一权威来源。
2. **App 是一等客户端，不是权威。** App 负责捕获意图、查看进度、批准高风险动作、验收结果；离线时可以有本地缓存，但缓存不是事实来源。
3. **执行器可插拔。** Codex、dsh、以及后续其他 harness 都是受控执行器；同一个任务可以更换执行器重试，任务本身不换、历史证据不丢。
4. **手机换机不丢进度。** 账本在 Mac，App 重装或换机后重新配对即可恢复视图。

这条决策不改动现有的项目、Markdown、Git 事实归属，也不引入云端控制面。

## 3. 三档授权

按动作影响面分档，默认最保守。分档判断由 Bridge 执行，App 只负责呈现与批准。

| 档位 | 包含什么 | 手机离线时 |
| --- | --- | --- |
| **A 档：只读与分析** | 读代码、读文件、检索、生成分析与提案 | 允许执行 |
| **B 档：可回收的写入** | 提交到工作分支、写临时产物、生成 Diff 待审 | 允许执行，回到 App 时汇报 |
| **C 档：不可回收或对外** | 写主分支、Push、删除、对外发送、花钱 | **一律停下等手机批准** |

补充规则：

- C 档动作即使手机在线，也必须在 App 内解锁后批准；通知不能直接批准。
- 分档不明确时归入 C 档。
- 降档需要用户显式确认；升档（放宽）永不自动发生。
- 任一动作升级到 C 档时，已经开始的执行必须停在安全点。

## 4. 降级与单点

Mini 是单点，产品必须显式处理它不可用的情况。

- **Mac 离线**：App 显示"Mac 离线、任务暂停"，不使用最后已知状态伪装成进行中。
- **Mac 重启**：进行中任务恢复到明确状态（继续、暂停或失败三选一），不允许重复执行同一动作。
- **账本导出**：账本必须能导出为单文件，可恢复到另一台机器。这是唯一副本，导出不是可选项。
- **不承诺高可用**：不做跨 Mac 集群、不做自动故障转移。

## 5. 后果

### 5.1 变好的部分

- 任务脱离 harness：失败后换执行器重跑，证据链保留。
- 手机离线不再是断点：长时间任务可以在 App 关闭期间推进。
- 夜间整理、定时任务、事件触发有了可运行的落点——这些能力此前卡在"没有常驻进程"。
- 与数据在本机、不接云的原则一致。

### 5.2 变差的部分

- Mini 成为唯一故障点；离线期间无法发起 B/C 档动作。
- Bridge 复杂度上升：从转发器变编排器，需要处理执行器生命周期、任务与执行尝试的分离。
- App 需要接受"本地缓存可能落后"这一事实，不能再用本地状态推断任务终态。

### 5.3 明确不做的取舍

- 不把账本搬到手机上（手机会关机，且换机即丢进度）。
- 不建云端控制面（数据离手、需要运维）。
- 不做隐藏双向同步。
- **不做自动重试。** 重启或中断后的任务一律停在"待确认"，由用户在 App 内决定是否重跑。

最后一条是刻意的取舍：自动重试会引入"同一次尝试是否已经生效"的问题，需要额外的尝试标记与对账机制。单用户场景下，让用户点一下的代价远小于重复 Push 或重复对外发送的代价。若将来要做自动重试，必须先具备可外部查验的尝试标记，再放开。

## 6. 验收标准

产品级、可观察，不依赖实现细节：

1. 手机全程离线 30 分钟，B 档任务继续推进；回到 App 看到完整时间线，事件序号无缺口。
2. 同一任务在 Codex 上失败后改派到 dsh 重跑成功，任务标识不变，两次执行的证据都可见。
3. 手机离线期间遇到 C 档动作，任务停在"等待批准"；手机上线后批准才继续，期间没有自动放行。
4. Mac 重启后，进行中任务一律转为"待确认"，不自动继续、不自动重试；由用户决定继续、重跑或放弃，且同一动作不重复生效。
5. Mac 关机时，App 显示明确的离线与暂停状态，不显示虚假进度。
6. 账本可导出并在另一台机器恢复，恢复后任务与证据可读。
7. 通知只能打开任务，不能直接完成 C 档批准。

## 7. 已知边界

- **不做自动重试，因此暂不需要"尝试标记 + 外部对账"机制。** 若将来放开自动重试，必须先补上：把尝试标识写入副作用本身（提交信息、分支名、远端 ref），重启后先按标记查验外部世界再决定，而不是凭本地记录推断。
- 执行器进程是否存活需要先判定再处理（进程标识 + 启动时间 + 进程 epoch），不允许盲目重启，否则可能出现两个进程同时操作同一工作区。
- 多设备同时在线时的写冲突；当前以单设备为主，需要在接入第二台设备前确认。
- Mini 硬盘或系统故障导致账本丢失的概率；导出频率与校验策略需要单独定。
